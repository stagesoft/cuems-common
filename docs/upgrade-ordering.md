# Upgrade ordering — what `cuems-common`'s upgrade does, in what order, and why

This is the ordering record the package's constitution (Principle III) requires: decided here,
written down, and kept true. Its central claims are asserted by `tests/test_postinst_ordering.py`
against the maintainer scripts themselves, not just described. **If the package's restart
behaviour changes, this document must change in the same commit.**

## 1. What the upgrade restarts, reloads, starts and stops

Measured from `debian/postinst`. Every action is guarded (`command -v`, `is-active`/`is-enabled`
where shown, `|| true`), so none can fail the upgrade.

| Action | Unit | Condition |
|---|---|---|
| **restart** | `systemd-journald.service` | only if active — applies the CUEMS journald drop-in |
| **restart** | `rsyslog.service` | only if active — applies the CUEMS rsyslog drop-in |
| **reload** | `apache2.service` (`invoke-rc.d`, else `systemctl`) | after enabling modules/sites |
| **reload** | `ssh.service` (`invoke-rc.d`, else `systemctl` if active) | last, after the organisation public key is installed for `cuems-admin` |
| **reload** | `avahi-daemon.service` | **only if the live discovery file actually changed** and the daemon is active (feature 001) |
| **start** | `rsync.service` | only on a controller (`/etc/cuems/master.ip`) whose `cuems-controller.target` is active |
| **stop** | `man-db.timer` | performance policy |
| **stop** (per logged-in user) | PipeWire / WirePlumber user units | so the shipped `/etc/systemd/user/` masks take effect immediately |
| **reenable** | `hostapd.service` | corrects its enablement symlinks; does not start it |
| **disable** | `apt-daily`/`apt-daily-upgrade` services and timers, `pppd-dns.service` | performance policy |
| **enable** only | `chrony`, `systemd-journal-remote`, `systemd-journal-upload`, `cuems-journal-vacuum.timer`, `cuems-cluster-poweroff`, `cuems-displays-on`, `cuems-gpu-pin`, `cuems-arm-wol` | never started here |
| `daemon-reload` / `deb-systemd-helper update-state` | — | unit files changed |

**Nothing in that list reads `/etc/cuems/network_map.xml`.** The services that do — the controller
and node engines, the editor, `cuems-nodeconf`, and at start-up `chrony` and
`systemd-journal-upload` through their hooks — are never restarted by this script.

`debian/postinst` carries no debhelper substitution token (only `debian/preinst` does), so
`dh_installsystemd` injects no autogenerated restarts either. That token must never be spelled out
in `postinst`, not even in a comment: `dh_installdeb` replaces it wherever it appears.

### The avahi reload, and why it is acceptable on a live host

The reload fires only when `cuems-migrate-avahi-service` actually rewrote the live discovery file,
compared by checksum before and after, and only when `avahi-daemon` is running. A reload re-reads
static service files and re-announces them; it does not restart the daemon. A host that may be
mid-show therefore sees at most one re-announcement, once, on the upgrade that migrates its file —
and none on any later upgrade, because the migration is idempotent.

## 2. The ordering decision

1. **The network-map conversion runs before every reader of the map that the script invokes.**
   Today that is only `cuems-write-chrony-source`, called near the end of `postinst`.
2. **The conversion runs before the live discovery-file migration.** The migration does not read
   the map; this order is for readability, not correctness.
3. **There is no conversion-versus-service-restart ordering to decide**, because no map-reading
   service is restarted by the upgrade (§1). Map readers pick up the converted map the next time
   they start — at reboot, or when an operator restarts them.

This replaces a deferral that had pointed at "feature 008" since feature 007 — a feature that
closed and was renumbered without anyone deciding. No maintainer script may defer a decision to a
feature number again; `tests/test_postinst_ordering.py` enforces that, while allowing provenance
labels such as `(feature 007, M3)`.

**When to revisit:** if §1 ever gains a restart of a map reader, the conversion must run before
it, and this section must say so.

## 3. The cluster upgrades as a unit

A CUEMS cluster is upgraded **as a unit**: every host in it to the same release, in one planned
operation, never mid-show. A staged rollout — some hosts upgraded, some not — is not supported.

That is a decision, and it is what makes one path safe that no package manager mediates:
**`cuems-engine` distributes project files from the controller to the nodes** (its deploy step
builds each project's `script.xml` into an rsync manifest and nodes receive it). A controller
whose documents are in a newer format pushes them to every node it deploys to, and a node running
older software would fail at show-load time, not at upgrade time. Because the cluster upgrades as
a unit, that host-to-host distribution is never mixed-version, and this package does not try to
sequence it.

The package relationships enforce what they can of this (`debian/control`: the `cuems-utils` bound
and the `cuems-nodeconf` `Breaks:`); the rest is operational discipline, stated here.

## 4. A node whose map names no controller

The package ships `/etc/cuems/network_map.xml` with an **empty** `<node_list/>` (feature 001,
FR-024). A fresh install before provisioning has that map, and so does a host that answered the
conffile prompt with the maintainer's version (its own topology is then at
`network_map.xml.dpkg-old`, already converted by `postinst` — restoring it is a copy).

On such a node — **designed outcome, not a fault**:

| Reader | What happens | In `systemctl --failed`? |
|---|---|---|
| `chrony.service` (hook `cuems-write-chrony-source`) | installs the client config, removes its own `sources.d/cuems-master.sources`, logs `WARNING: … names no controller`, exits 0; chrony runs **with no cluster time source** | no |
| `systemd-journal-upload.service` (`ExecCondition` `cuems-log-collector-url --check`) | the condition logs the same warning and exits 1, so systemd **skips** the unit | no |

Provisioning the map — from `/usr/share/doc/cuems-common/network_map.xml.example` — and restarting
those two units ends it. A map that is *missing*, *unparseable*, or names a controller with an empty
`<ip>` still fails both units loudly, as before: those are faults.

Before feature 001, the shipped map carried a placeholder controller at `192.168.1.10`. Both readers
silently resolved to that address, which nothing answers, and chrony ran pointed at it.

## 5. Recorded, not done: stop shipping the map as a conffile

Feature 001 **empties** the shipped map rather than **de-registering** it. Emptying removes the
damage — taking the maintainer's version can no longer install a wrong topology. De-registering
would remove the prompt itself, by treating `network_map.xml` the way this package already treats
`/etc/avahi/services/cuems.service`: a live, host-owned file kept in the repository but not shipped,
with `postinst` installing a starter only when the path is absent.

The smaller change came first because it fixes the harm with one file's content and no maintainer
script mechanics, in a release that already carries a discovery cutover.

**The only acceptable mechanism for the larger change** — constitution Principle VI, 1.0.1:

- **Not** a bare `dpkg-maintscript-helper rm_conffile`. On a modified copy it moves the live file to
  `.dpkg-bak`; on an unmodified one it deletes it. For the file that holds a cluster's topology,
  that is the `1.3.0-20` outcome for `/etc/network/interfaces`, which left hosts with no network at
  their next reboot.
- **The `1.3.0-22` pattern instead**: snapshot the live file in `debian/preinst`, de-register the
  conffile, and in `debian/postinst` restore the snapshot **only if the path is empty** — exactly
  how `/etc/network/interfaces` is handled today (see the preinst/postinst blocks for that file).
